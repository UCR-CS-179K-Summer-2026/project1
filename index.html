System Architecture

Streamline is built around two independent parsers, not one. The first is the JSON parser from Sprint 1 — a Scanner tokenizes raw text and a Parser builds a tree of JSONValue nodes (each one a tagged std::variant). The second, added this sprint, is a completely separate query-language parser — its own QueryScanner and QueryParser — that turns a query string like FILTER(GET("gpa") > 3.5) | LIMIT(5) into an expression tree, which an execution engine then walks, one pipeline stage at a time, against the uploaded document.

Classes & Data Model

JSONValue is a single concrete class wrapping a tagged std::variant<ArrayValue, bool, nullptr_t, double, ObjectValue, string>. getType() derives the ValueType straight from variant::index() (the enum's declaration order is kept in sync with the variant's alternative order), and every caller downstream — lookup(), formatValue() — reads the payload with std::get<T>(value.getValue()) once the type is known.

Previous structure: polymorphism

Sprint 1 started with JSONValue as an abstract base class with a virtual getType(), and one concrete leaf class per ValueType — JSONNull, JSONBoolean, JSONNumber, JSONString, JSONArray, JSONObject. Every node was heap-allocated behind a JSONValuePtr (unique_ptr<JSONValue>), and arrays/objects held vector<JSONValuePtr> / vector<pair<string, JSONValuePtr>> — a pointer per child rather than the child itself.

Polymorphism (before)Variant (now)
Per-node cost 1 heap allocation + vtable pointer per node No allocation, no vtable — the tag is 1 byte inline
Type dispatch getType() is a virtual call (indirect, through the vtable) variant::index() — a direct integer load
Reading a value Downcast (or an already-known concrete type) to reach the field std::get<T>(value.getValue()), checked against a closed set of alternatives
Tree layout Graph of heap nodes linked by unique_ptr — pointer-chasing to traverse JSONValues live directly inside the parent's vector — contiguous, cache-friendly
Extensibility Add a new ValueType by adding a new subclass Add a new ValueType by adding a variant alternative (touches every switch/visit, which the compiler flags as non-exhaustive)

For a JSON tree with thousands of nodes, the polymorphic version did thousands of individual heap allocations (one make_unique per value) and paid a vtable-pointer's worth of memory on every single node, including leaves like a lone true or a short number. Traversing the tree meant chasing pointers across whatever the allocator scattered them across, which is unfriendly to the cache. The variant version allocates once per vector's backing storage (amortized across all of that container's children) instead of once per value, drops the vtable pointer entirely, and keeps sibling values next to each other in memory. Since our whole premise (per the README) is staying fast and low-memory on large files, that tradeoff was worth making even though it meant giving up some of the OOP ergonomics — isString()/isArray()-style helpers, for example, are gone, replaced by a single switch(getType()) at each call site.

The honest tradeoff in the other direction: sizeof(JSONValue) is now at least as big as its largest alternative (ObjectValue, a vector of key/value pairs) plus a small tag, so a node that's "just a bool" is heavier in isolation than a bare JSONBoolean used to be. That cost is paid once per node either way (inline now vs. on the heap before) — it's a wash on a small tree, and a clear win once the allocation count and pointer-chasing start to dominate on a large one.

A second, parallel data model: the query's expression tree

JSONValue represents data. Queries need their own tree to represent a program — FILTER(GET("gpa") > 3.5) is a small expression, and QueryParser builds it the same variant-based way Sprint 1's data model works: an ExpressionNode is a tagged std::variant, and every node lives in one flat vector, referenced by a NodeId (an index into that vector) rather than by pointer.

ExpressionNode
variant<BooleanOperand, StringOperand, NumberOperand, GetOperand, BinaryOperand>
▼
BooleanOperandtrue / false literal
StringOperand"literal" text
NumberOperandnumeric literal
GetOperandvector<string_view> path
BinaryOperandop, NodeId left, NodeId right

BinaryOperand is what makes FILTER(GET("a") > 0 AND GET("b") == 2) possible: it doesn't hold its operands directly, it holds two more NodeIds — so a comparison, an AND, and an OR are all the same struct, and evaluating one just means recursively evaluating whatever nodes its left and right point at. A separate QueryFunction variant (Get/Filter/Sort/Limit/GroupBy/Average) represents the pipeline stages themselves, each one pointing into this same node vector for whatever expression it needs (a FILTER's condition, a SORT's target field, and so on).

Module Interfaces

Scanner (Jules)

Turns raw text into one Token at a time, on demand, rather than tokenizing the whole input up front. Tracks its own line number and knows whether it's scanning a .json or .jsonl buffer, so it can phrase errors accordingly.

enum class TokenType : uint8_t {
    Boolean, Colon, Comma, End, LBrace, LBracket,
    Null, Number, RBrace, RBracket, String
};
enum class ParserType { JSONL, JSON };

struct Token {
    TokenType type;
    string_view value;  // view into the original buffer, no copy
    Token(TokenType t, string_view v);
};

class Scanner {
public:
    Scanner(string_view json, ParserType type);
    int getLineNumber() const;
    Token scan();  // advances and returns the next token
};

Parser & data model (Jules)

Recursive-descent parser: one parse() call per JSON value, recursing for nested objects/arrays. JSONValue is returned by value now — a tagged variant, not a heap-owned pointer.

enum class ValueType : uint8_t { Array, Boolean, Null, Number, Object, String };

using ArrayValue = vector<JSONValue>;
using ObjectValue = vector<pair<string, JSONValue>>;

class JSONValue {
public:
    explicit JSONValue(ArrayValue a);
    explicit JSONValue(bool b);
    explicit JSONValue(nullptr_t n);
    explicit JSONValue(double d);
    explicit JSONValue(ObjectValue o);
    explicit JSONValue(string s);

    ValueType getType() const;
    const variant<ArrayValue, bool, nullptr_t, double, ObjectValue, string>& getValue() const;
};

class Parser {
public:
    Parser(string_view json, ParserType type);
    JSONValue parse();
};

Query parser (Jules)

Its own recursive-descent grammar, entirely separate from the JSON parser above. parsePipeline() splits on |; each stage's parseFilter()/parseSort()/etc. builds ExpressionNodes as needed and pushes one QueryFunction.

class QueryParser {
public:
    explicit QueryParser(string_view query);
    void parse();

    const vector<ExpressionNode>& getExpressionNodes() const;
    const vector<QueryFunction>& getFunctions() const;
};

Session & execution engine (Ryan & Javier)

Session holds the uploaded document; excecuteQuery() runs a query string against it and returns the formatted result (or a formatted error) as one string — no exceptions escape past it for a malformed query, they're caught by the caller in main.cpp.

struct Session {
    JSONValue file = JSONValue(nullptr);
    bool isInitialized = false;
    void initialize(JSONValue v);
};

void uploadFile(const string& path, Session& session);
string excecuteQuery(Session& session, string query);

struct LookupResult {
    bool ok;
    const JSONValue* value;  // valid when ok == true, non-owning
    string error;            // valid when ok == false
};

LookupResult get(const JSONValue& value, const vector<string_view>& path);
string formatResult(const LookupResult& result);

Edge Case Handling

The JSON-parsing edge cases from Sprint 1 (below) still apply unchanged. The query engine added a second layer of edge cases on top — several of them found by actually trying to break the five operations, not anticipated up front.

CaseBehavior
File not found / can't open Throws std::runtime_error with a suggestion (check path, permissions, working directory).
Unterminated string / bad token in scanner Scanner::scan() throws runtime_error — "Unterminated string" regardless of file type; otherwise "Invalid JSON input at line N" for .json or "Invalid JSONL input" for .jsonl.
Illegal escape sequence / raw control character in a string Scanner rejects both explicitly rather than passing them through — \uXXXX is validated for length, and bytes below 0x20 require an escape.
\uXXXX above the Basic Multilingual Plane (emoji) A high/low surrogate pair is combined into the real code point and UTF-8-encoded correctly. Comparing an emoji field with FILTER(... == "🍉") works; a bare GET on that field still prints the escaped form rather than the rendered character.
FILTER where some records are missing the field Those records just don't match — the query still returns a result instead of erroring on the first gap.
SORT where a record is missing the sort field Deliberately stricter than FILTER: there's no sane position for a record with no value, so this is a clean error instead of a silent skip.
SORT comparing incompatible types (string vs. number) Clean Error: cannot compare... — this used to be an uncaught exception that crashed the whole program; found and fixed this sprint.
AVERAGE on a non-numeric field, or on zero usable values Both are clean errors now ("field is not a number", "no numeric values found") — also previously an uncaught crash.
GROUPBY where the key field is itself an array/object That one record is excluded from every group instead of crashing the whole query.
Malformed query syntax QueryParser::parse()'s exception is now caught by the CLI, printing a readable error and returning to the menu instead of exiting the program.
Known gaps, not yet fixed: a multi-record .jsonl upload only captures its first record right now (Session holds one JSONValue, and the file is parsed as a single document rather than line-by-line the way Sprint 1's readJsonlFile() did). A bare scalar value followed by trailing content (e.g. "a": 1 with no wrapping braces) can also slip through unrejected. Neither crashes anything — both are correctness gaps we know about and are choosing to leave for a follow-up rather than rush before the demo.

Query Language

All six operations below are implemented and pass a live regression suite (see Build System). Every result on this page was run against the actual binary — not hand-written.

Get done

Retrieve the value at a given path. Multiple arguments walk into nested objects/arrays.

Query
GET("student","name")
JSON
{"student":{"name":"Ryan","scores":[90,85]}}
Result
"Ryan"

Filter & Comparison done

Keep only the records matching a boolean expression — comparisons combine with AND/OR, not just one condition.

Query
FILTER(GET("a") > 1)
JSON
[{"a": 1, "b": 2}, {"a": 2, "b": 2}]
Result
[{"a": 2, "b": 2}]
Also works
FILTER(GET("major") == "CS" AND GET("gpa") > 3.5)

Sort done

Order an array of records by a field, ascending or descending.

Query
SORT(GET("a"), ASC)
JSON
[{"a": 1, "b": 2}, {"a": 0, "b": 3}]
Result
[{"a": 0, "b": 3}, {"a": 1, "b": 2}]

Limit done

Return only the first N records.

Query
LIMIT(1)
JSON
[{"a": 1, "b": 2}, {"a": 0, "b": 3}]
Result
[{"a": 1, "b": 2}]

GroupBy done

Bucket records by the value of a field.

Query
GROUPBY(GET("a"))
JSON
[{"a": 1, "b": 2}, {"a": 0, "b": 3}, {"a": 1, "b": 5}]
Result
{"1": [{"a": 1, "b": 2}, {"a": 1, "b": 5}], "0": [{"a": 0, "b": 3}]}

Average done

Compute the mean of a field. Works standalone (one number) or right after GROUPBY (one number per group, same code path).

Query
GROUPBY(GET("city")) | AVERAGE(GET("price"))
JSON
[{"id":1,"city":"Riverside","price":450000}, {"id":2,"city":"Riverside","price":480000}, {"id":3,"city":"Los Angeles","price":800000}, {"id":4,"city":"Riverside","price":460000}]
Result
{"Riverside": 463333.33, "Los Angeles": 800000}

Piping, chained without limit done

| threads one stage's output into the next. There's no fixed cap on how many stages can chain — tested up to 50 in a row with no issue.

Query
FILTER(GET("gpa") > 3.9) | SORT(GET("gpa"), DESC) | LIMIT(3)
Behavior
Each stage sees the previous stage's result, not the original document — a stage checks whether it got the shape it needs (array vs. object) and errors cleanly if not.

Algorithms & Optimizations

Recursive-descent parsing

Parser::parse() mirrors the JSON grammar directly: one function, one switch on the current token type, recursing into itself for nested object/array values. No lookahead beyond a single token is needed.

Lazy, single-token scanning

Scanner::scan() is pulled one token at a time by the parser instead of tokenizing the whole input into a vector up front. Memory used by tokenization stays O(1) regardless of input size — it doesn't grow with how much of the file has been scanned.

Zero-copy tokens

Token::value is a string_view into the original buffer — scanning a string or number allocates nothing. A copy only happens once, when the parser commits to building a string-valued JSONValue (or an object key) and needs an owned std::string.

Value-typed tree, moved not copied

JSONValue is a value type (a tagged variant), and sub-trees live directly inside their parent's vector (ArrayValue/ObjectValue). They're still std::moved into place as they're built rather than copied, so building the tree doesn't duplicate data — it just no longer requires a heap allocation (unique_ptr) per node the way the earlier polymorphic design did.

Per-line parsing, whole-file buffering

readFile() now reads the entire file into an in-memory std::string (ostringstream buffer; buffer << file.rdbuf();) before readJsonlFile()/readJsonFile() parse it — .jsonl is still parsed one line at a time via a fresh Parser per line, but that line comes out of the buffered string rather than being streamed with std::getline straight off the file handle.

Sort-key precomputation (Schwartzian transform)

A naive SORT comparator calls GET on both sides of every comparison — for n records that's O(n log n) field lookups. SORT instead looks up each record's key exactly once before sorting, into a vector<pair<const JSONValue*, size_t>>, and sorts that — O(n) lookups, with the comparator itself doing nothing but comparing two already-known values.

Hash-map grouping

A naive GROUPBY finds-or-creates a record's bucket by scanning every group seen so far — O(records × groups) in the worst case. GROUPBY instead keeps an unordered_map<string, size_t> from group key to bucket index, so placing each record is O(1) average regardless of how many distinct groups exist.

Measured, not assumed: parsing json/students.json (85,032 records) takes ~550–580 ms either way — the JSON parser itself didn't get faster this sprint, and there wasn't a real lever to pull there (it's already a single-pass O(n) recursive-descent parse). Where the optimizations above actually matter: a FILTER that matches nearly every record and prints the full result added ~520 ms on top of parsing — almost entirely copying and formatting the result set — versus ~40 ms for a FILTER that matches nothing at all. The per-record evaluation logic is already cheap; large result sets are where the cost actually lives.
Not yet optimized: FILTER/GROUPBY still deep-copy every matching JSONValue into the result set, rather than carrying indices/pointers until the very end. lookup()/get() still does a linear scan over an object's entries for every field access — fine at typical object sizes, a candidate to revisit if that stops being true.

Build System

Sprint 1 was built with one g++ ... command per person, copy-pasted from a comment at the top of each driver file (demo.cpp, test_lookup.cpp). That already went stale once — a leftover reference to the pre-rename jsonl-reader.cpp broke test_lookup.cpp's documented build command after the file became file-reader.cpp, and nothing caught it until someone actually tried to build it. As of Aug 2, the whole project builds through one root-level CMakeLists.txt instead.

Why CMake instead of hand-typed g++ commands

Four reasons this was worth adopting mid-sprint rather than staying with manual commands:

Manual g++CMake
File list lives in a comment per driver, can silently go stale File list lives in CMakeLists.txt — the thing that actually builds, can't drift from itself
Every invocation recompiles every source, every time Incremental — cmake --build build only recompiles what changed
Flags (-std=c++17 -Wall -Wextra) depend on whoever typed the command remembering them Flags are set once in CMakeLists.txt, applied to every target automatically
No optimization flag in any documented command — compiles at the default, -O0 Defaults to a Release build — see below

Layout & usage

CMakeLists.txt lives at the repo root and now builds four targets from week2/ — streamline is the CLI, tests is the regression suite, benchmark is the performance harness referenced in Algorithms & Optimizations, and w1tests keeps Sprint 1's original code building on its own, untouched, from week1/ — kept around deliberately as a record of where the project started, not folded into the current codebase. 

cmake -B build           # configure once
cmake --build build       # (re)build — only recompiles what changed
./build/streamline        # opens the menu
./build/tests              # regression suite
./build/benchmark           # performance harness

Both streamline and tests compile the same CORE_SOURCES — scanner.cpp, parser.cpp, file-reader.cpp, integration.cpp, version.cpp, query-parser.cpp — so the test suite is exercising the exact same engine the CLI runs, not a separate copy.

A build that silently didn't build: for a stretch this sprint, query-parser.cpp was missing from CORE_SOURCES — every other file compiled fine, and the failure only showed up at the final link step (undefined symbols: QueryParser::parse()), which is easy to miss if you only skim compiler output for the word "error" on the wrong line. It recurred more than once after a fresh pull before it stuck — worth checking CORE_SOURCES first if a fresh clone ever fails to link.
